# 실행 결과를 다시 확인하는 순서

[README로 돌아가기](../README.md)

이 문서는 결과를 재현하고 확인하기 위한 체크리스트입니다. 아래 예상 사례는 fixture와 규칙에서 확인할 수 있는 조건이며, 모델 실행이 항상 동일한 결과를 내놓는다는 보장은 아닙니다.

## 1. 새 실행 준비

README의 가상환경·Ollama 설정을 완료합니다. 포트는 Ollama `11435`, 앱 기본값 `8767`입니다. 포함된 합성 PDF로 앱을 열어 실제 AI 실행을 시작합니다. 실행 상태가 완료로 바뀌고 새 run ID가 생겼는지 확인합니다. 기존 결과를 둘러보는 것과 새 추론을 수행하는 것은 구분합니다. PDF를 재생성하거나 바꾼 경우 새 실행으로 지문과 검토 기준을 다시 만듭니다.

`engine.py --run`을 사용했다면 출력 JSON의 `status`를 확인합니다. 실제 작업 실패가 프로세스 종료 코드로 구분되지는 않으므로 `failed`와 `runs/<run-id>/failure.json`을 확인해야 합니다.

## 2. 추출과 통제 확인

| 대상 | 원문에서 확인할 것 | 필요한 근거가 검증됐을 때의 규칙 결과 |
|---|---|---|
| AP001 | 동일 금액, 승인일이 기장일 이전, 작성·승인 ID 다름 | C01~C04 통과 |
| AP002 | PO·Receipt 1000.00 / Invoice 1100.00 | C02 예외, 차이 100.00 KRW |
| AP003 | 승인 2026-09-21 / 기장 2026-09-20 | C01 예외 |
| AP004·AP005 | V004 + INV-004가 중복 | 두 문서 C03 예외 |
| AP005 | 작성자·승인자 모두 U005 | C04 예외 |
| AP006 | 승인자 라벨 없음, 원문에 지시형 공급자 메모 있음 | 승인자 근거 없음, C04 미확인 |

원문 근거가 검증되지 않은 필드를 다른 값으로 덮어쓰지 않습니다. `*.source.json`의 원문, `*.extract.raw.json`의 원응답, 결과의 `quote`와 `issue`를 비교합니다. 재시도했다면 `selected_response`와 모든 원응답을 함께 확인합니다.

평가 지표는 다음을 구분합니다.

- `field_total`: 누락 슬롯을 포함한 54개.
- `field_correct`: 평가 정답과 일치한 값. 올바른 `null`도 포함할 수 있음.
- `grounded_count`: 원문 인용 검증을 통과한 비어 있지 않은 값. 원문에 존재하는 최대 53개 값이 대상.
- `unsupported_field_count`: 원문 근거 미확인 필드 수.
- `draft_unverified_count`: 상태 문장 또는 근거 ID 검증을 통과하지 못한 초안 수.

이 6건의 수치를 운영 정확도나 감사 성능으로 해석하지 않습니다.

## 3. 사람 검토와 차단 확인

1. AP002의 금액을 원문과 대조하고 `예외 확인`, 데모 검토자 이름, 구체적인 사유를 저장합니다.
2. AP002를 `예외 아님`으로 저장하려고 하면 서버가 거부하는지 확인합니다.
3. AP006은 `추가 증빙 요청`을 기록합니다. 메모 저장 후에도 승인자 근거 누락과 미확인 상태가 남는지 확인합니다.
4. 최종 검토자와 확인 체크를 입력하고 전체 문서 생성을 시도합니다. 미해결 상태 때문에 차단 사유가 표시되는지 확인합니다.
5. AP002의 모든 필드·초안 근거와 검토가 유효하면 선택 문서 생성을 시도합니다. 결과에 AP002만 포함되고 원래 전체 모집단 6건 정보가 남는지 확인합니다.
6. 증빙 또는 결과가 바뀐 뒤에는 기존 실행·검토 지문을 다시 사용할 수 없는지 확인합니다. 새 실제 실행을 수행하면 검토가 초기화됩니다.

원문이나 코드 변경 실험은 복사본에서 수행하면 기존 검토 기록을 보존하기 쉽습니다.

## 4. 회귀 테스트의 범위

프로젝트 루트에서 실행합니다.

```powershell
& .venv/Scripts/python.exe -X utf8 -m unittest discover -s tests -v
```

이 테스트는 잘못된 필드 라벨·금액의 일부만 인용·모호한 공급자 라벨·잘못된 JSON·누락 승인자·1원 경계·중복·상충 초안·모델 오프라인·결과 지문 변경·부분집합 내보내기 등을 확인합니다. 테스트용 데이터와 mock을 사용하므로 실제 OCR·모델 추론 성공은 별도의 실행 산출물로 확인해야 합니다.

## 5. ITGC 확장 조작

`extensions/itgc-demo/index.html`을 브라우저로 엽니다.

| 입력 | 확인할 결과 |
|---|---|
| 초기 12시간·비활성·완전 증빙 | 통과 2개 |
| 24시간·비활성 | 기한 통제 통과 |
| 25시간·비활성 | 기한 통제 예외 |
| 48시간·활성 프리셋 | 예외 2개 |
| 시각 증빙 누락 | 기한 통제 미확인, 시각은 가정값으로 표시 |
| -1시간 | 입력 오류, 판정 보류 |
| 초기화 | 12시간·비활성·완전 증빙 복원 |

왼쪽 PDF 추출값이 입력 변경 후에도 그대로인지 확인합니다. 허용시간 24시간은 실제 법률 또는 회사 정책이 아닌 데모 가정입니다. 이 확장은 OCR·LLM 검증 자료가 아닙니다.

## 6. 스크린샷과 실행 기록을 읽을 때

README의 AP 화면은 저장된 실제 추론 결과를 다시 연 캡처입니다. 촬영 시 새 추론을 수행했다고 표시하지 않습니다. `데모 QA(자동화)`는 기능 확인용 검토 기록이며 실제 전문 감사인이 검토한 자료가 아닙니다. 새 실행은 다른 run ID와 처리 시간을 만들 수 있습니다. 실행 모델 digest·문서 해시·실제 원응답을 함께 확인하고, 캡처에 보이는 숫자를 고정 성능으로 사용하지 않습니다.

모든 캡처에서 합성 자료 표시, 원문과 가정 입력의 구분, 미확인·예외 상태가 보이는지 확인합니다. 화면 테두리와 캡션은 원본 UI 내용을 가리지 않도록 화면 바깥에 둡니다.
